# What is the project

Project to learn and practice golang and enterprise pattern architecture with AI.

## Stack

- Go 1.26
- HTTP router: `github.com/go-chi/chi/v5`
- Response rendering: `github.com/go-chi/render`
- Database (dependency added, not yet wired): `go.mongodb.org/mongo-driver/v2`
- API docs: `swaggo/swag` generates Swagger 2.0 into `./docs/`, rendered by `go-scalar-api-reference` at `/reference`
- A Swagger 2 -> OpenAPI 3 conversion is served at `/openapi.json`

## Project layout

```
cmd/server/main.go                # entrypoint; general swag annotations live here
internal/
  apierrors/                      # shared error type used across modules
    types.go                      #   AppError{Code, Message}, ProblemDetails
  openapi/                        # swagger 2 -> openapi 3 conversion handler
  modules/
    <module>/                     # one folder per domain (e.g. video)
      handler.go                  #   Register<Module>Routes(*chi.Mux) - the only place routes are declared
      usecases/                   #   one file per use case (e.g. upload.go, get_video.go)
        <action>.go               #   exported func, takes primitive args, returns (*apierrors.AppError)
docs/                             # generated by `swag init` - do not edit by hand
files/                            # local storage for uploaded files (gitignored)
```

## Architecture guidelines

- The code is structure around modular architecture to create an architecture both easier for developers and AI to understand
- After implementing features make sure the code is correct and running by running `go build`

## Module convention

A module is a self-contained vertical slice:

1. `handler.go` defines `Register<Module>Routes(r *chi.Mux)` and groups every endpoint under a versioned prefix (e.g. `/api/v1/content`).
2. Each use case lives in its own file under `usecases/` as an exported function. Handlers parse the request, call the use case, and translate the result into `render.Status` + `render.JSON`.
3. Use cases return `*apierrors.AppError` (or `nil`). Handlers map it to a status. Do not return plain `error` from use cases.
4. Swag annotations (`@Summary`, `@Tags`, `@Router`, `@Param`, `@Success`, ...) live directly above the route function in `handler.go`, not in `main.go`.

## Coding conventions

- Standard Go style: `gofmt` and `go vet` clean.
- No linter is configured yet. If one is added, document the command in the table below.
- Errors from use cases use `*apierrors.AppError{Code, Message}`. Wrap lower-level error text into `Message`; do not leak internal error strings to the response.
- Handlers take `http.ResponseWriter, *http.Request`. Pass `r.Context()` to anything that may block (DB calls, file IO).
- No package-level mutable state for request data. The current `db` map in `internal/modules/video/handler.go` is a placeholder - replace it with a repository backed by MongoDB when the persistence layer is added.
- Route registration is centralized in `handler.go`. Do not register routes from use case files.

## API documentation workflow

`docs/` is generated. Any time you add, rename, or remove a route, or change a request/response contract, regenerate it:

```bash
swag init -g ./cmd/server/main.go -o ./docs
```

Requires the `swag` CLI. Install once with:

```bash
go install github.com/swaggo/swag/cmd/swag@latest
```

Make sure `$(go env GOPATH)/bin` is on your `PATH` (Windows PowerShell: `;((go env GOPATH) + '\bin')`).

## Gaps to be aware of

- No tests exist yet (`*_test.go`). The first one added should also set the testing convention (table-driven, testify, etc.) here.
- MongoDB driver is in `go.mod` but unused. The current `db` map in the video module is a stub.
- `internal/apierrors/middleware.go` is a commented-out stub. The error handling path is currently: use case returns `*AppError` -> handler picks a status and renders it directly.
